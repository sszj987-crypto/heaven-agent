# 对话语音交互修复设计

## 目标

修复对话页将用户录音过程表现为助手说话、语音错误被伪装成助手消息、文字回复被音频状态隐藏，以及播放失败无反馈的问题。

## 交互设计

- 按住麦克风时，在用户侧显示“你正在说话…”。
- 松开后，在用户侧显示“正在识别你的语音…”。
- 识别成功后，将真实转写作为用户消息，再显示助手回复。
- 识别失败时显示独立的语音错误状态，不插入助手角色消息。
- 助手文字始终默认显示。
- 助手有可用音色时显示“播放语音”；首次点击时才请求 TTS，不自动生成或播放。
- 首次生成的音频在当前页面内缓存，后续点击直接复用。
- 生成中显示“正在生成语音…”，失败时在对应助手消息下显示可重试错误。

## 状态与数据流

对话页将全局 `loading` 拆分为明确阶段：

- `idle`：可输入和录音。
- `recording`：正在采集用户声音。
- `transcribing`：上传并识别用户声音。
- `replying`：LLM 正在生成回复。

助手消息保留文字、记忆来源和安全状态，并新增按消息保存的 TTS 参数、音频 URL、生成状态与播放错误。文字消息和语音消息采用同一套助手展示逻辑。

首次点击播放时调用 `/chat/audio`。前端拒绝空 Blob；后端在音频为空或 TTS 异常时返回明确的非 2xx 错误，避免把不可播放内容当作成功 WAV。

## 错误处理

- 麦克风权限失败：保留明确权限提示。
- ASR/LLM API 失败：使用后端统一错误消息，显示为非角色化状态。
- TTS 生成失败：保留助手文字，播放按钮允许重试。
- 浏览器拒绝播放或音频解码失败：显示“语音播放失败，请重试”，不吞掉异常。
- 页面卸载或清空会话时释放所有 Blob URL，并停止当前音频。

## 测试

- 前端纯状态测试：用户录音/识别阶段位于用户侧；助手文字默认可见；语音只在点击后进入生成状态。
- API 客户端测试：`fetchAudio` 拒绝空响应并保留后端错误。
- 后端 API 测试：TTS 异常和空音频返回错误，不返回成功的空 WAV。
- 回归验证：前端测试、ESLint、TypeScript、production build，以及后端相关 API 测试与全量测试。
